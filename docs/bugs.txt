是，主要原因是 **Folo 有云端历史数据库**，而 Reader 当前只抓订阅源此刻返回的 XML。

- Reader 分页本身没有总页数上限：单源每页 20 条、聚合每页 40 条，会一直读取本地 SQLite，直到本地数据耗尽。
- 但多数 RSS/RSSHub 接口一次只返回最近 10～100 条。Reader 新增订阅时只能入库这些内容，无法凭普通 RSS 获取更早文章。
- Folo 服务端长期定时抓取并积累历史条目；同一 feed 还可能早已被其他用户订阅，因此新用户也能分页看到大量云端历史数据。
- Reader 后续刷新不会删除旧文章，所以使用时间越长，本地历史也会逐渐累积。

因此当前看到的“滚动上限”通常是**本地已入库文章数量上限**，不是前端分页硬限制。

若希望接近 Folo，需要增加历史回填来源，例如：
1. RSSHub 路由支持分页时主动抓取多页；
2. 接入有历史归档的服务端 API；
3. 自建后台定时抓取并长期保存。

仅靠标准 RSS XML，通常无法补齐源站未返回的旧文章。

## 一、相对 Gopeed 的差异

### 已接近 / 已落地
- **HTTP**：多连接 Range、慢启动、work-stealing、Method/Body、代理接线（约 75–85%）
- **队列**：状态机、`maxRunning`、localStorage 持久化、pause/continue/delete
- **IPC**：`create/resolve/pause/continue/delete/eval_js/extract_archive/copy_extension` 主路径已通
- **归档**：zip/tar/tgz 原生；7z/rar 依赖系统工具
- **Webhook / 脚本**：有实现；脚本 UI 弱

### 明显缺口
| 缺口 | 相对 Gopeed | 迁移可行性 |
|------|-------------|------------|
| HTTP 分片账本 / 连接级 Stats / Prefetch | 深度差 | **中** — 在现有 `http.rs` 上加深 |
| BT 行为级兼容（anacrolix 语义、DHT/PEX、做种细节） | 现用 librqbit | **中→难** — 「能用」易；bit-exact **不现实** |
| ED2K 全协议（server.met、DHT、压缩分片、Client 状态） | 仅询源+分片子集 | **难 / 近阻塞** — 缺成熟 Rust 等价物，需长期自研或 FFI |
| 扩展：goja 全 polyfill、Blob 桥、TLS fingerprint、WebView 自动化 | 现有 Boa + XHR/fetch 子集 | **难**；WebView 自动化 **短中期宜非目标** |
| 存量扩展生态兼容 | 无 `__gopeed_*` / Blob URL 约定 | **难** — 需兼容层或放弃官方扩展商店兼容 |
| REST API / History / 多端壳 | 仅 Solid 壳内页面 | **易→中** — 产品层可补，非引擎硬伤 |
| 配置 UI：trackers、doneScripts、缺文件清理逻辑 | 模型有、接线不全 | **易** |

**Gopeed 迁移建议：** 以 HTTP+队列+归档+Webhook 为「产品可用」基线；BT 保持「librqbit 能用」；ED2K/WebView 扩展单独立项，勿绑死主验收。

## 二、相对 yt-dlp 的差异

### 已有
- YoutubeDL 编排子集：`extract_info`、`-f`/`-S` 子集、cookie 文本/平台 jar
- **手写精品 IE（13）**：YouTube（ejs+WebPO）、B 站/番剧、Twitter、TikTok、Douyin、Vimeo、Twitch、Soundcloud、IG、Reddit、Niconico、Generic
- **注册表 ~2034**：URL 匹配面对齐 `_extractors.py`（对表约 100%）
- remux：系统 ffmpeg + 可选 `media-ffmpeg` stream-copy

### 核心真相：生成 IE ≠ 站点能力
每个生成类实质是：

`下网页 → OG / JSON-LD / m3u8 / mp4 正则`（`_ported_real_extract`）

复杂站会抛 `[port] … mechanical body expand pending`。这是 **软 stub**，不是上游逻辑移植。

### 大块缺口与可行性

| 缺口 | 影响 | 可行性 |
|------|------|--------|
| **~2000 IE 真实 `_real_extract` 体** | 站点对等主战场 | **极难** — 无法靠再跑转译器一次解决；应按站族/CDN 后端手写加深 |
| **FileDownloader 栈**（HttpFD / HlsFD / Dash / Fragment / RTMP / WS / 直播专用） | 分片、AES-HLS、直播 | **难** — 须在 Rust/TS 自建；现靠 HTTP 引擎 + ffmpeg HLS |
| **common.py / utils 深度**（JWPlayer、SMIL、ISM、Nuxt、登录/geo 全家桶） | 一批站连锁失败 | **中→难** — 可按调用热度补 helper |
| **TLS impersonate**（curl_cffi） | WAF/CDN | **中→难** — 需 Rust/原生 TLS 指纹能力 |
| **cookies-from-browser / netrc / Adobe Pass** | 鉴权站 | **中** |
| **PP 全集**（Fixup、章节、EmbedThumbnail、Exec、SponsorBlock 真实现） | 后处理对等 | **中** — Merger 等已有壳；SponsorBlock 仍 stub |
| **playlist / archive / download_ranges / outtmpl 全语义** | CLI 对等 | **中** |
| **YouTube 子 IE**（Playlist/Tab/Search…） | 仅主视频手写强 | **中** — 可沿手写 Youtube 族扩展 |
| **与上游持续 rebase** | IE 高频变更 | **持续成本** — 钉版本 + re-port，不是一锤子 |

**yt-dlp 迁移建议：** 停止把「registry 满」当完成态；优先级应为 **手写高价值站 + Fragment/HLS 下载 + common helpers**，生成壳仅作 URL 路由与偶然命中。

## 四、结论

1. **Gopeed**：引擎主路径已从「脚手架」进入「可用子集」；差距集中在 **ED2K 深度、扩展生态、BT 行为细节、产品周边（REST/History）**。迁移 **可行且应分期**，ED2K/WebView 宜降级。
2. **yt-dlp**：URL 面与运行时外形已齐；**真正缺口是提取方法体 + 分片下载器 + common/networking**。当前「全量生成 IE」只解决了匹配与兜底刮页，**不能**当作站点对等。
3. 文档：应用 `bugs.txt` 的偏低结论更新为现状；把 `DOWNLOAD_MODULE.md` 中「全量转译落地」改为「全量注册 + 刮页壳 + 手写覆盖」。

若下一步要动手，建议先定一条验收线：**「产品可用」**（HTTP/BT/队列/13+ 手写站 + HLS 分片）还是 **「上游行为对等」**（会把 ED2K/全 IE/扩展 WebView 拉进主路径）。两条线的工期差一个数量级。
